1. EXECUTIVE SUMMARY & VERIFICATION BOUNDARY
------------------------------------------------------------------------------
The safety audit for Feature 3 (In-App Notifications) performed read-only probes
against the live Supabase instance.

API ACCESSIBILITY BOUNDARY:
- PostgREST REST API exposes public tables and public RPC functions.
- PostgREST REST API strictly BLOCKS access to PostgreSQL internal catalogs
  (e.g., information_schema.table_constraints, pg_policies, pg_triggers, pg_indexes).
  Attempts to access pg_* or information_schema directly return HTTP errors
  because internal catalogs are not exposed over the REST API by design.
- As a consequence, internal catalog queries (foreign keys & delete rules, RLS
  policy definitions, triggers, and unexposed functions) must be run via the
  Supabase SQL Editor using `supabase/inspect_schema.sql`.

DECISION CONFIRMATION:
- Existing events with society_id = NULL remain UNCHANGED (no backfill or DML).
- Strict admin-to-event society authorization is PRESERVED:
  Status notifications will reject any request if the caller's society_id is NULL,
  if the event's society_id is NULL, or if they mismatch.

4. INTERNAL SYSTEM CATALOGS (SUPABASE SQL EDITOR REQUIRED)
------------------------------------------------------------------------------
Because PostgREST denies client-side querying of PostgreSQL internal catalogs,
the following checks cannot be executed via the REST API and must be retrieved
via the Supabase SQL Editor using `supabase/inspect_schema.sql`:

Query 1: Table Columns, Types & Nullability
  - Target: information_schema.columns
  - Purpose: Confirms exact underlying PostgreSQL data types and nullability constraints.

Query 2: Primary Keys & Unique Constraints
  - Target: information_schema.table_constraints & key_column_usage
  - Purpose: Validates PK on users(id), events(id), participants(id), and UNIQUE(event_id, user_id).

Query 3: Foreign Key Constraints & ON DELETE Rules
  - Target: information_schema.referential_constraints
  - Purpose: Confirms participants -> events foreign key delete action.
    Validates that notifications -> events(id) can use ON DELETE SET NULL without conflict.

Query 4: Existing Indexes
  - Target: pg_indexes
  - Purpose: Validates existing indexing on participants(event_id, user_id) and events(status).

Query 5: Row Level Security (RLS) Status & Policies
  - Target: pg_policies
  - Purpose: Captures exact existing policies on users, events, participants, societies.
    Ensures notifications RLS policies do not interfere with existing tables.

Query 6: Existing Database Triggers
  - Target: information_schema.triggers
  - Purpose: Confirms no existing triggers on participants (INSERT) or events (UPDATE)
    conflict with trigger_notify_participant_joined or trigger_notify_event_status_changed.

Query 7: Existing Stored Functions / Routines
  - Target: information_schema.routines
  - Purpose: Dual verification that no existing procedures share migration function names.
